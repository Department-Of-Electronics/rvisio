# Bare-metal template for the RVisio SoC

> **New to RVisio?** The step-by-step guide is in the simulator: System on chip (SoC) → **📘 VS Code guide** →
> **▶ How to run**.

The smallest C project for the RVisio system on chip, without an operating system: startup code, linker
script, register definitions and a `main.c` that prints over the UART and counts on the LEDs. Copy this folder
to start your own bare-metal program.

```
main.c      your program (output over UART0, a counter on the GPIO LEDs)
soc.h       addresses and registers of the board "SoC: Flash + SRAM + DRAM, UART, SPI, I2C, GPIO, timer, sensor" (generated by RVisio)
crt0.S      reset: stack pointer, .bss, call main, stop with ebreak
link.ld     memory map: code in Flash, data and stack in SRAM
Makefile    make -> app.elf, app.lst (disassembly)
.vscode/    debugging from VS Code over the simulator's GDB server (Windows + WSL, Windows + xPack, Linux)
```

## Build and run

```bash
make                         # app.elf
```

RVisio → **System on chip (SoC)** → **📂 ELF** → `app.elf` → **⏭ To end**. The text appears in the
**Console** panel, the counter on the LEDs in **Sensors and actuators**.

## Debug from VS Code

1. RVisio → **System on chip (SoC)** → **🐞 GDB server**. A **code** appears.
2. If RVisio does not run on your own computer (for example rvisio.com), start the bridge in this folder and
   leave it running (the script is in `tools/` at the root of the repository, or download it in RVisio:
   📘 VS Code guide → Materials):
   * Linux: `python3 ../../tools/rvsim-gdb.py CODE`
   * Windows with WSL: `wsl python3 ../../tools/rvsim-gdb.py CODE` (with `wsl` in front: GDB runs in WSL)
   * Windows without WSL: `py ..\..\tools\rvsim-gdb.py CODE`

   The bridge talks to https://rvisio.com by default; for another address add `--server <address>`.
3. VS Code: File → Open Folder → **this folder** (with the Makefile and .vscode, not the whole repository),
   Run and Debug (Ctrl+Shift+D) → choose the configuration → **F5**.
   The program is built, GDB attaches to 127.0.0.1:3333, erases the memories, loads the program and stops at `main`.
4. Breakpoints, F10/F11, variables and registers work as on a real board; the browser shows the whole SoC,
   and the **Program** panel lists the code GDB loaded with the current instruction highlighted.

Debug console: `-exec monitor reset`, `-exec monitor erase`, `-exec info registers`, `-exec x/8wx 0x10000`.

## What to install (once)

* **Windows with WSL (recommended):** `wsl --install -d Ubuntu-24.04` (PowerShell as administrator), then in Ubuntu
  `sudo apt update && sudo apt install -y gcc-riscv64-unknown-elf gdb-multiarch make python3`; VS Code with the
  **C/C++** extension. Configuration **SoC, Windows (WSL)**.
* **Windows without WSL:** xPack RISC-V GCC (riscv-none-elf-gcc) and xPack Windows Build Tools (make), Python 3;
  configuration **SoC, Windows (xPack, no WSL)**.
* **Linux:** `sudo apt install -y gcc-riscv64-unknown-elf gdb-multiarch make python3`; configuration **SoC, Linux**.

Both Windows routes need Windows 10 or 11 (64-bit). WSL also needs Windows 10 version 2004 or later,
administrator rights for the installation and virtualization turned on in the BIOS (it often does not work
inside a virtual machine). xPack needs neither, so it suits lab computers and locked laptops.

## Your own board

`soc.h` and `link.ld` describe the default board. If your teacher assigned you another board (different
addresses or peripherals), download its `soc.h` in RVisio (📘 VS Code guide → Materials) and replace this one.
